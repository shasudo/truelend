# Tier A Characterization Test Plan

Revised to a ~120-test target (down from the original 353), per this rule applied per Tier A file:

**KEEP:** the authorization check (who's refused, where they're sent) · one happy path · each distinct failure branch that produces a DIFFERENT observable outcome (different redirect, status code, DB write, or error shape) · anything involving money, KYC state transitions, or data mutation.

**CUT:** input variations on the same branch · validation-library behavior (zod's own parsing rules) · assertions on error message strings · framework-behavior assertions · "does it call X" spies that just restate the implementation.

**Final total: 132 tests across 23 files** (was 353; net +6 over the original 126 target — 3 for the where-scoping addition, +2 because admin's `lead-actions.ts`/`team-actions.ts` each needed one more test than planned to properly cover a second exported action, +2 because both apps' `kyc/upload/route.ts` were missing a real `tx.delete()` test wrongly cut in the original plan as "the same DB-write shape as update-existing", +2 because partners' auth route and health/ready route each have one extra distinct-outcome branch admin's don't (the blocked-raw-signup 404 and the registration-schema sub-check), −3 for all three apps' `app/api/health/route.ts` being cut as genuinely trivial — a static one-liner a build already catches, not padding to hit a number). Files exceeding the ~8/file default are individually justified below. **All Tier A characterization tests are done: admin (57), partners (64), website (11).** Coverage-scoped-to-Tier-A and the pre-Phase-1 gate are the remaining items before Tier A is declared complete — see the bottom of this file.

## Assertion discipline (applies to every test below)

Per the "must survive the refactor" directive: assert only on **observable outcomes** — return values, thrown errors, redirect targets, HTTP status, and the exact arguments passed to the DB layer (this last one is fair game precisely because it's what a mutation-correctness bug would corrupt). Do **not** assert on internal call sequences, private helpers, function names, file paths, or intermediate-value shapes. Import through each module's public entry point. If a future file move would force an edit to a test, the test is wrong today.

## Shared infrastructure — status

The drizzle double lives in `packages/test-support` (`@truelend/test-support`), shared by all apps rather than copy-pasted — it's a generic db/tx fake with nothing app-specific in it, including a callable `$client` tagged-template (postgres.js's real raw-query shape, added for website's `lib/lead-actions.ts`'s ref-code lookup) plus a `rawQueryRows` option to configure what it resolves to. Per-app: `fake-auth-dependencies.ts` (mocks each app's own `lib/auth.ts` dependencies — `createAdminAuth`/`createPartnerAuth`, `getCloudflareContext`, etc. — deliberately NOT shared, since these seams genuinely differ per app), `fake-partner-context.ts` (partners-only, the `withPartnerMutation` seam), `fake-next-cache.ts` (`revalidatePath` no-op stub), `fixtures.ts` (partners-only, `buildPartnerRow`). `apps/website` has no `lib/auth.ts` wrapper, so its `fake-website-dependencies.ts` mocks `getCloudflareContext` and the rest of its module-level dependencies directly.

### `@truelend/test-support`'s fake-drizzle fidelity — what these tests do and don't prove

It's a hand-rolled chainable double, not a real (or in-memory) Postgres. Every test using it inherits its assumptions. A test can pass against the fake while real drizzle/Postgres behaves differently — that risk is accepted, not eliminated, so it's written down here rather than left implicit:

**What it models:** `.select().from(table).where(...).limit(...).for(...)` resolving to a row array keyed by the real schema table object's identity (see the where-clause caveat below); `.update(table).set(values).where(...)` and `.delete(table).where(...)` recording the call and resolving; `.insert(table).values(values)` recording the call, resolving directly when awaited, and separately exposing `.returning(...)` resolving to a configurable row array; `.transaction(async tx => {...})` invoking the callback with a fresh fake `tx`, or rejecting outright when a test configures `transactionError` to simulate a mid-transaction failure.

**What it does NOT model:**

- **Row locking.** `.for("update")` is a no-op — it never actually blocks anything. These tests cannot catch a race condition between two concurrent transactions; they only prove single-request-at-a-time logic.
- **Real transaction rollback semantics.** A configured `transactionError` makes the fake never invoke the callback at all (or throw before/around it) — there is no modeling of "statement 1 committed, statement 2 failed, Postgres rolled the whole transaction back atomically." Partial-write-then-rollback behavior specific to a real transaction isn't distinguishable here from "nothing ran."
- **Real driver error shapes.** `transactionError` is whatever plain value a test passes in — not a real `postgres` package error (no error codes, no constraint-violation shape). Tests can't validate branching on a specific Postgres error type.
- **SQL correctness, mostly.** `.where(eq(...))` conditions can be — and by default are — accepted and completely ignored: `rowsByTable`'s map values are typically a plain array, returned regardless of what the real `where` clause would actually filter. A bug in the real condition (wrong column, wrong operator) would not be caught by most tests in this plan.

**The one place that blindness is deliberately closed: ownership/authz reads.** A `rowsByTable` entry can also be a `FakeRowProvider` function receiving the captured `{table, whereArgs, limitArgs}`, letting a test return a row ONLY when the query is structurally scoped as expected (checked via `node:util`'s `isDeepStrictEqual` against a real `eq(...)` call built with the expected id) and `[]` otherwise. This matters because a plain array can't tell the difference between "the query correctly filtered by session.user.id" and "the query returned the first row in the table to anyone who asked" — exactly the failure mode that would leak one partner's data to another, and a plausible Phase 3 casualty since restructuring touches these call sites. **Applied:** `apps/partners/lib/auth.ts`'s partner-profile lookup (`requirePartnerSession`, `withPartnerRequest` — 3 tests: correctly-scoped, a different session's id doesn't leak another partner's row, and the same proof for `withPartnerRequest`'s structurally different code path); `apps/admin/app/api/kyc/[...key]/route.ts`'s document lookup (proving a mismatched/unreferenced R2 key 404s rather than returning the first `partnerDocuments` row in the table — the exact thing the route's own comment says it must never become: "a generic authenticated R2 reader"). **Not applicable:** `apps/admin/lib/auth.ts` has no equivalent drizzle read to scope-test — staff/admin status comes directly from `session.user.role` (better-auth's own session payload), not a separate database lookup. Everywhere else in this plan, `where()` stays ignored — a plain array is enough when the filter isn't the security boundary, and using the function form there would just be noise.

In short: these tests prove the Server Action's own branching logic, the shape of what it hands to the DB layer, and — where explicitly applied — that an ownership-scoped read is actually scoped. They do not prove the SQL is correct everywhere, that concurrent access is safe, or that a real Postgres transaction would behave as assumed.

**Two hard-won findings, now load-bearing for every file below:**

1. **`mock.module()` must be registered by calling an exported function from the test file itself — never as a side effect of importing a separate file.** Doing the latter with two or more mocks active reproducibly crashes Node 24.18's test runner with an internal assertion (`loadCJSModuleWithModuleLoad`). Every support file exports an explicit `install*Mock()`; every test file calls those, then dynamically `await import()`s the module under test (a static import would bind the real, unmocked dependency before the installs run). This is now enforced mechanically, not just by convention: `@typescript-eslint/no-restricted-imports`, configured once in `packages/eslint-config/test-guardrails.js` and wired into all three apps, bans static imports of `lib/*-actions`, `lib/auth`, `middleware`, and `app/api/**/route` from any `test/**/*.test.ts` file (type-only imports are exempt).
2. **Runtime vs. installed types disagree.** Node 24.18 prefers `mock.module(specifier, { exports: {...} })` and warns `namedExports` is deprecated — but the repo's installed `@types/node` only declares `namedExports`, so `exports` fails to typecheck. Using `namedExports` for now, documented at each call site as the one line to flip once `@types/node` catches up. `engines.node` in the root `package.json` is pinned to `~24.18.0` (was `>=24 <25`) — tight enough to stop the API drifting across a minor/major Node bump while `mock.module()` is experimental, loose enough to still take `24.18.x` patch releases (`.npmrc` has `engine-strict=true`, so an exact pin would hard-fail installs on every patch bump). All three apps' test scripts run with `--experimental-test-module-mocks`.
